지난주에는 방화벽을 적용하는 기능과 WireGuard 설정을 비교하는 기능이 각각 있었습니다. 이번 목표는 DB에 등록한 VPN 주소를 서버의 실제 설정에 반영하는 것입니다. WireGuard만 주소를 바꾸면 방화벽이 예전 주소를 허용할 수 있기 때문에 두 설정을 함께 맞춰야 합니다. 정상 적용뿐 아니라 중간 오류가 발생했을 때 함께 돌아오는지, 재부팅해도 유지되는지, 작업 결과가 기록되는지까지 확인했습니다.

VPN 주소 실제 변경

DB 목표 주소 변경→서버·클라이언트 반영→실제 웹 접속 확인
처음에는 기존 10.40.0.2 주소를 10.40.0.3으로 수동 변경했습니다. DB의 할당 주소, 서버의 Peer AllowedIPs, Windows 터널의 Address를 맞췄습니다. 서버 자신의 주소 10.40.0.1은 변경하지 않았습니다. 방화벽도 새 출발지 주소를 허용하도록 적용했습니다. 왼쪽은 DB와 서버 설정이 일치하는 결과이고, 오른쪽은 실제 접속의 출발지 주소가 .3이며 TCP 80 연결에 성공한 결과입니다. 설정 비교와 실제 통신을 함께 검증했습니다.
13주차 / 04

WireGuard 주소 적용 자동화

DB의 목표 주소를 서버 WG의 실행 중 설정과 저장 파일에 함께 반영합니다.

자동으로 처리하는 작업

① 기존 실행 주소와 설정 파일 백업
② Peer 주소와 wg0.conf 변경
③ DB·실행 중·저장된 주소 일치 확인

두 설정을 함께 바꾸는 이유

실행 중 설정은 현재 통신에 사용하고,
저장 파일은 WG 재시작 시 불러옵니다.

대상: 기존 Peer 1개
DB·방화벽·Windows 주소 변경은 별도 수행

사진: 의도적인 오류 후 복구 시험

.3 → .4 적용·검증 → 시험용 오류 발생
실행 주소와 저장 파일을 이전 .3으로 복구

DB 목표 주소는 자동 복구하지 않아 별도로 되돌렸습니다.

이 페이지는 DB에 지정한 목표 주소를 서버 WG에 자동 반영하는 프로그램입니다. 실행 중인 WG는 지금 통신에 사용하는 설정이며, 저장 파일은 WG를 다시 시작할 때 읽는 설정입니다. 둘을 함께 바꿔야 재시작 후에도 변경이 유지됩니다. 프로그램은 현재 상태를 백업하고, DB의 목표 주소를 실행 중인 Peer AllowedIPs와 wg0.conf에 반영한 뒤 일치 여부를 검사합니다. 사진은 .3에서 .4로 실제 변경하고 검증한 직후 시험 옵션에 따라 일부러 오류를 발생시킨 결과입니다. 시험 지점 도달은 변경과 검증을 마쳤다는 뜻이며, 그 뒤 실행 주소와 저장 파일을 백업 기준인 .3으로 복구했습니다. DB는 자동 복구하지 않아 별도로 .3으로 되돌렸습니다. Windows 클라이언트 주소와 방화벽은 이 프로그램의 변경 대상이 아닙니다. 현재 구현은 기존 Peer 1개를 대상으로 합니다.
13주차 / 05

WireGuard·방화벽 통합 적용

전체 백업→WireGuard 주소 적용→방화벽 적용·저장

한 명령으로 서버 설정 반영

wg-update-network.py --apply
규칙 생성·주소 반영·방화벽 검사·적용·저장

작업 범위

DB는 관리자가 목표 주소를 지정
Windows 터널 주소는 별도로 수정

방화벽 단계에서 실패해도 앞서 변경한 WireGuard까지 복구하도록 구성했습니다.

두 명령을 단순히 연속 실행하면 두 번째 명령이 실패했을 때 첫 번째 변경이 남을 수 있습니다. 그래서 전체 작업 이전 상태를 별도로 백업하는 통합 프로그램을 만들었습니다. 실제 실행 순서는 사전 확인, 공통 백업, DB 기반 방화벽 후보 생성, WireGuard 적용, 방화벽 적용, 재부팅용 저장, 최종 WireGuard 비교와 방화벽 파일 문법 검사입니다. 기존 프로그램의 함수를 재사용하고 기존 Peer 적용 잠금과 방화벽 통합 잠금을 잡습니다. 다만 DB 수정과 개별 명령 전체를 완전히 하나의 잠금으로 통합한 것은 아니므로 이번 시험은 다른 변경을 동시에 수행하지 않는 조건에서 진행했습니다.

정상 적용과 통합 복구 시험

정상 실행은 변경한 설정을 유지합니다. 복구 시험은 적용·저장까지 마친 뒤 일부러 오류를 내서 작업 전 상태로 되돌립니다.

오른쪽 복구 시험을 먼저 수행한 뒤 왼쪽 정상 적용을 진행했습니다. DB는 별도 명령으로 복원했고, 규칙 수가 아닌 시험 옵션의 의도적인 오류로 복구를 실행했습니다.

오른쪽은 통합 복구 시험입니다. DB 목표 주소를 .5로 지정하고 WireGuard와 방화벽을 실제로 적용하고 저장했습니다. 이후 test-after-save 옵션에 따라 의도적으로 예외를 발생시켰습니다. 복구 대상 네 항목이 각각 작업 전과 일치하는지 확인했고 웹 접속도 다시 성공했습니다. DB는 프로그램이 자동으로 복원하지 않으므로 별도 명령으로 .4로 되돌렸습니다. 이 시험 이후 왼쪽처럼 시험 옵션 없이 .4에서 .5로 정상 적용했습니다. Windows 주소도 .5로 맞춘 뒤 웹 접속을 확인했습니다. 규칙이 없어서 실패한 것이 아니라, 저장이 끝난 뒤 코드가 의도적으로 오류를 발생시킨 시험입니다.

DB 변경 이력과 실제 적용 이력

기존 management_audit

DB에서 무엇을 바꿨는지 기록
예: VPN 할당 .5 → .6

새 network_apply_runs

실제 서버 적용이 어떻게 끝났는지 기록
예: 정상 완료 또는 오류 후 복구

기록 항목저장 내용
작업 식별·시간run_id, 시작·종료 시간, 요청 계정
대상·진행기기, 변경 전·목표 주소, 진행·실패 단계
결과·복구성공 여부, 오류 내용, 백업 위치, 종료 코드
DB 주소 변경이 성공해도 실제 서버 적용은 실패할 수 있습니다. 그래서 기존 management_audit와 별도로 network_apply_runs 테이블을 만들었습니다. 스키마 변경 전 SQLite 백업과 무결성 검사를 수행했습니다. wg-apply-history.py가 wgmonitor 계정으로 DB에 시작, 진행, 종료 정보를 저장하고 통합 프로그램이 이를 호출합니다. run_id는 작업마다 생성되는 UUID 식별 번호로 인증 비밀값은 아닙니다. 미리보기는 이력을 생성하지 않고 실제 적용부터 기록합니다. 작업 시작 기록에 실패하면 적용을 시작하지 않도록 했습니다.
