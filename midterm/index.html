03 / 결과 처리

허용: 내부 서버로 전달·응답 반환
차단: WG-DROP 기록 남김

패킷의 통과 여부는 Gateway의 WireGuard·nftables가 결정합니다. Python·SQLite는 남은 로그를 저장하고 조회합니다.

주소는 현재 실습 예시입니다. 암호화 구간은 PC↔Gateway입니다. 로그 속도 제한으로 모든 차단 패킷이 기록되지는 않습니다.

윗부분은 개발 예정인 관리 기능이며 일반 사용자 트래픽이 통과하는 장비가 아닙니다. 현재 기반에서는 Windows PC가 Gateway의 UDP 51820으로 암호화된 통신을 보냅니다. WireGuard가 등록된 상대와 통신을 확인한 뒤 복호화하고, nftables가 내부 웹 TCP 80 허용 여부를 판단합니다. 허용된 요청은 내부 서버로 전달되며 응답은 Gateway와 VPN 터널을 거쳐 PC로 돌아옵니다. 차단된 요청은 WG-DROP으로 기록될 수 있고 rsyslog·Python·SQLite가 그 기록을 관리합니다. 로그 속도 제한 때문에 모든 차단 패킷이 남는 것은 아닙니다. Python 프로그램이 각 웹 요청을 실시간으로 승인하는 구조는 아닙니다.

WG-DROP은 어디서 붙을까?

허용 규칙 아래의 log prefix "WG-DROP: "이 차단 로그에 이름을 붙입니다. 뒤의 drop은 패킷을 차단합니다.

limit rate 5/second burst 10 packets는 기록이 너무 많이 쌓이지 않도록 로그 속도를 조절합니다.

WG-DROP 로그 → rsyslog → /var/log/wireguard-access.log

규칙 순서가 중요합니다. 로그 속도 제한을 넘는 패킷도 기본 정책으로 차단되지만 로그는 남지 않을 수 있습니다.

nftables의 forward 체인에 기본 차단 정책을 두었습니다. 첫 번째 허용 규칙은 이미 허용된 연결의 응답·관련 패킷을 통과시킵니다. 두 번째 허용 규칙은 wg0에서 ens34로 가는 10.40.0.2의 10.30.0.10 TCP 80 새 연결만 통과시킵니다. 나머지는 WG-DROP 표시를 붙여 기록하고 차단하는 규칙을 만납니다. 이때 limit rate 5/second burst 10 packets는 기록 속도를 조절하는 부분이며, 제한 초과 패킷도 기본 drop 정책으로 차단됩니다. counter는 규칙에 맞은 패킷 수를 셉니다. rsyslog가 WG-DROP 기록을 전용 파일로 분리합니다. 아래 사진은 Gateway에서 출력한 실제 forward 체인입니다. 화면의 packets·bytes 숫자는 촬영 당시의 누적값이며 고정 설정값이 아닙니다.

연결부터 복구까지 확인한 뒤,
허용된 사용자의 과도한 요청에도 대응할 수 있는지 검증하겠습니다.

1. 등록된 WireGuard 클라이언트는 연결되고 미등록 키는 연결되지 않는지 봅니다. 2. 현재 정책에서는 내부 웹 TCP 80만 허용하며 SSH와 ICMP는 차단됩니다. 3. WG-DROP 로그가 SQLite에 저장되고, 같은 원문을 다시 처리해도 중복 저장되지 않는지 봅니다. 로그 속도 제한으로 모든 차단 패킷이 기록되는 것은 아닙니다. 4. 재부팅 후 서비스와 자동 저장이 살아나는지, 백업본을 별도 시험용 DB로 복원해 읽을 수 있는지 봅니다. 실제 일일 예약 백업 실행과 복원은 아직 검증하지 않았습니다. 5. 관리 프로그램을 구현하면 클라이언트 등록·해제와 정책 변경이 실제 설정에 반영되는지 봅니다. 자동 설치 기능을 도입하면 재실행 시 키와 DB 보존, 실패 후 재개를 확인합니다. 6. 소유한 격리 VM에서 요청 속도·실행 시간·중지 조건을 미리 정하고 웹 응답·서버 부하를 비교합니다. 요청량 제한 기능을 도입한 경우에만 제한 시점과 정상 사용자 영향을 측정합니다. 한 PC의 시험은 분산 공격 검증이 아닙니다. 1분 주기 DB 저장 시각을 차단 시각으로 사용하지 않습니다.
