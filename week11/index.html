기기 정보와 접근 정책 수정

기기 단위 관리

  • 기기 이름 수정
  • 활성·비활성 상태 변경
  • 비활성 기기의 규칙 생성 제외

서비스 단위 관리

  • 개별 정책 활성·비활성 변경
  • 목적지·프로토콜·포트 수정 코드
  • 포트 80 → 8080 → 80 시험

목적지·프로토콜 수정은 코드 구현, 포트 변경은 실행 검증까지 완료했습니다.

기기 이름을 바꿨다가 원래대로 복원하고, 활성 상태를 바꿨을 때 규칙 생성 대상에서 제외되는지 확인했습니다. 기기 전체를 중지하는 것과 개별 서비스 권한을 중지하는 것도 구분했습니다. 정책에서는 목적지와 프로토콜, 포트를 수정할 수 있도록 만들었고, 실제 시험은 포트를 80에서 8080으로 바꾼 뒤 80으로 복원했습니다. 미리보기 규칙의 포트도 함께 바뀌었습니다. 이때 실제 서버의 포트나 방화벽을 바꾼 것은 아닙니다.

VPN 주소 변경과 이력 보존

할당 순서VPN 주소처리 결과
최초 할당10.40.0.2종료 시각 기록
테스트 할당10.40.0.3종료 시각 기록
원래 주소 복원10.40.0.2현재 할당

이전 할당은 종료 처리하고 새 행을 추가합니다. 마지막 행이 현재 할당입니다.

첫 시험 당시 결과입니다. 이후 시험에 따라 이력은 누적됩니다. 실제 VPN 접속·종료 기록이 아닙니다.

주소를 바꿀 때는 기존 값을 덮어쓰지 않고 이력을 남기도록 했습니다. 이전 할당에 종료 시각을 넣고 새 할당을 추가합니다. 시험에서는 10.40.0.2를 10.40.0.3으로 변경하고 다시 원래 주소로 복원했습니다. 그 결과 첫 시험에서 세 개의 기록이 남고 마지막 할당만 현재 상태가 됩니다. 종료 시각이 없다는 것은 유효한 DB 할당이라는 의미이지 현재 접속 중이라는 뜻은 아닙니다. 실제 WireGuard 주소는 변경하지 않았고, 이력 보관 기간 제한도 아직 적용하지 않았습니다.

관리 변경 내역 자동 기록

관리 정보 수정→변경 전후 값 기록→함께 저장
저장 항목예시
작업·대상access_rule.edit / 정책 1번
변경 전destination_port: 80
변경 후destination_port: 8080
추가 정보변경 시각(UTC) · 실행 계정

공통 함수 record_change()를 네 가지 수정 프로그램에 연결했습니다.

실행 계정 wgmonitor는 실제 사람의 관리자 로그인 신원과는 다릅니다.

주소 할당 이력만으로는 기기 이름이나 정책 변경을 모두 확인할 수 없어서 management_audit 테이블을 추가했습니다. 공통 함수 record_change가 변경 시각과 작업 종류, 대상, 변경 전후 값을 저장합니다. 예를 들어 포트 수정은 80에서 8080으로 바뀐 내용을 JSON 형태로 남깁니다. 기기 수정, 정책 상태, 정책 조건, VPN 할당 변경의 네 경로에 연결했습니다. 현재 기록하는 계정은 실행 계정 wgmonitor이며, 사람별 관리자 인증은 앞으로 별도로 연결해야 합니다.

잘못된 입력 검증

포트 70000 입력→범위 검사→입력 거부

확인한 결과

  • 오류와 올바른 범위 안내
  • DB 수정 전에 중단
  • 성공 변경 기록 추가 없음

다음 페이지의 실패 복구 시험

이번: 잘못된 값을 DB 수정 전에 거부
다음: 수정 도중 오류가 나면 전체 취소

이번 실행 검증은 포트 범위 오류 사례입니다. 모든 입력 오류를 시험했다는 뜻은 아닙니다.

이번에는 잘못된 포트 값을 입력했습니다. 70000은 허용 범위를 벗어나므로 argparse 오류와 사용법이 표시되고 DB에 연결하기 전에 종료됩니다. 따라서 기존 정책과 성공 변경 기록은 그대로입니다. 이것은 DB를 수정한 뒤 되돌리는 롤백 시험과 다릅니다. 다음 페이지에서는 수정 이후 기록 저장이 실패하는 상황을 시험합니다.

저장 실패 시 전체 변경 취소

시험용 DB 복사→기록 저장 오류 유발→변경 전후 비교

기기 수정 · 정책 상태 · 정책 조건 · VPN 할당 4개 시험 통과

기록 저장에 실패하면 정보 수정도 함께 취소됩니다.

운영 DB는 변경하지 않았습니다. 백업 복원이나 모든 장애 상황을 시험한 것은 아닙니다.

정상 처리뿐 아니라 기록 저장이 실패하는 상황도 확인했습니다. 운영 DB를 읽기 전용으로 복사한 뒤, 복사본에 변경 기록을 저장할 때 오류가 발생하도록 장치를 넣었습니다. 실제 수정 프로그램을 복사본 대상으로 실행하고 시험 전후의 테이블 값을 비교했습니다. 기기 수정과 두 가지 정책 변경, VPN 할당 변경 모두 원래 상태로 돌아왔습니다. 특히 VPN 할당은 이전 기록의 종료와 새 기록 추가도 함께 취소됐습니다. 이것은 트랜잭션 롤백 시험이며 정전이나 디스크 손상까지 모두 검증한 것은 아닙니다.
