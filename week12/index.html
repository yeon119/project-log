MAC 주소를 쓰지 않는 이유

WireGuard 터널을 통해 PC의 MAC 주소가 전달되지 않습니다.

MAC 주소

같은 네트워크 구간에서 프레임을 전달하는 데 사용합니다. 유선·Wi-Fi 인터페이스마다 다를 수 있습니다.

프로젝트의 관리 기준

기기 ID에 공개 키와 VPN 주소를 연결합니다. WireGuard는 키로 상대를 인증하고, 방화벽은 VPN 주소로 접근 정책을 적용합니다.

3계층에서 확인할 수 있는 정보

IPv4 헤더 · 출발지·목적지 IP, 패킷 전체 길이, TTL(남은 경유 한도), 상위 프로토콜 번호(TCP·UDP·ICMP 등)

실습 로그와 DB · 차단 기록에서 출발지·목적지 IP, 프로토콜, 길이 등을 저장합니다. TCP·UDP 포트와 TCP 플래그는 4계층 정보입니다.

RFC 791 §3.1 · IPv4 헤더 형식

IPv4 헤더에는 출발지와 목적지 IP 외에도 패킷 전체 길이, TTL, 상위 프로토콜 번호가 있습니다. TTL은 라우터를 거칠 때 줄어드는 값입니다. 이번 실습의 DB는 차단 로그에서 IP, 프로토콜, 길이 등을 추출해 저장합니다. 포트와 TCP 플래그도 기록할 수 있지만 이 값들은 4계층에서 가져옵니다. MAC 주소는 유선 랜카드나 무선 랜카드처럼 네트워크 인터페이스에 붙는 주소입니다. 같은 네트워크 구간에서 이더넷 프레임을 전달할 때 쓰입니다. 우리 실습에서 Windows가 WireGuard 터널로 내부 웹 서버에 요청을 보내면, Gateway가 복호화해서 처리하는 것은 출발지와 목적지 IP가 들어 있는 IP 패킷입니다. 이 패킷에는 Windows 랜카드의 MAC 주소가 실려 있지 않습니다. 이전 실습의 차단 로그에서 MAC 항목이 비어 있었던 것도 이 구조와 연결됩니다. 우리 프로그램은 DB에서 기기 ID에 WireGuard 공개 키와 VPN 주소를 연결합니다. 예를 들어 client-001은 관리 화면과 DB에서 사용하는 기기 번호입니다. WireGuard는 등록된 공개 키를 기준으로 그에 맞는 개인 키를 가진 상대를 인증합니다. 방화벽은 터널에서 나온 패킷의 VPN 주소와 목적지, 포트를 보고 접근을 허용할지 결정합니다.

같은 WireGuard 설정 사용같은 공개 키 · 10.40.0.2같은 공개 키 · 10.40.0.2

연결 방식을 바꿔도 같은 터널 설정이면 동일한 등록 기기로 관리합니다.

예를 들어 Windows PC 한 대에 유선 랜카드와 Wi-Fi 랜카드가 있다고 가정하겠습니다. 유선으로 접속할 때와 Wi-Fi로 접속할 때 사용하는 인터페이스가 다르고, 각각의 MAC 주소도 다를 수 있습니다. 유선에서 Wi-Fi로 전환하면 Gateway가 보는 접속 출발지 IP나 UDP 포트도 바뀔 수 있습니다. 하지만 Windows에서 같은 lab-Client 터널 설정을 사용하면 공개 키와 터널 안의 주소인 10.40.0.2는 유지됩니다. 따라서 이 프로젝트에서는 유선과 Wi-Fi를 바꿔도 같은 client-001로 관리합니다. 여기까지가 기기 관리 기준이고, 이제 그 기준으로 등록한 정책을 방화벽에 어떻게 적용했는지 보여드리겠습니다.

DB 정책을 방화벽에 적용

DB의 활성 정책 조회→규칙 파일 생성→검사 후 적용
정책허용 규칙 수새 웹 연결
비활성화0개시간 초과
다시 활성화1개HTML 응답

잘못된 설정 파일은 검사에서 거부됐고 기존 웹 접속은 유지됐습니다.

먼저 DB에서 활성 기기의 현재 VPN 주소와 활성 접근 정책을 읽어 nftables 규칙을 생성했습니다. 이번 실습에서는 client-001의 VPN 주소인 10.40.0.2에서 내부 서버 10.30.0.10의 TCP 80번 포트로 가는 새 연결을 허용했습니다. 생성한 규칙 파일은 검사한 다음 Gateway에 적용했습니다. 정책을 끄고 다시 생성했을 때 웹 허용 규칙이 0개가 됐고, 적용 후 Windows에서 새 웹 요청을 보내니 연결 시간이 초과됐습니다. 정책을 다시 켜고 적용하자 허용 규칙이 1개로 돌아왔고 내부 서버의 HTML을 받을 수 있었습니다. 일부러 문법 오류를 넣은 파일도 시험했습니다. 검사에서 걸러졌고 기존 웹 접속은 계속 가능했습니다.

재부팅 후에도 정책 유지

현재 규칙 저장→/etc/nftables.conf→부팅 시 nftables가 불러옴

Gateway 재부팅 후에도 웹 접속 허용 · SSH 접속 실패를 확인했습니다.

저장 프로그램은 현재 규칙을 디스크에 기록합니다. 다음 부팅 때 systemd가 nftables 서비스를 시작하면, 서비스가 이 파일을 읽어 커널에 규칙을 다시 적용합니다.

재부팅 과정에서는 Python 스크립트를 다시 실행할 필요가 없습니다. 앞서 저장한 설정을 nftables 서비스가 읽습니다. 실행 중인 방화벽 규칙은 커널 메모리에 있습니다. 재부팅 후에도 같은 정책을 쓰려면 디스크에 설정을 남겨야 합니다. 그래서 기존 설정을 백업한 뒤 현재 방화벽 규칙을 재부팅용 파일로 만들고, 검사에 통과하면 /etc/nftables.conf에 저장하도록 했습니다. Gateway가 켜질 때 systemd가 nftables 서비스를 시작하면 이 파일을 읽어 커널에 규칙을 다시 등록합니다. 실제로 Gateway를 재부팅한 뒤 nftables와 WireGuard가 모두 active인 것을 확인했습니다. Windows에서 내부 웹페이지 HTML을 다시 받았고, 동일 서버의 SSH 포트 연결은 실패했습니다. 방화벽의 기본 전달 정책과 웹 허용 규칙도 재부팅 후에 확인했습니다.

한 명령으로 적용하고 실패 시 복구

생성→백업·검사·적용→재부팅용 저장

이전에는 규칙 생성, 백업·검사·적용, 재부팅용 저장을 각각 실행했습니다. 이제는 통합 명령 한 번으로 세 단계가 순서대로 실행됩니다.

복구 후 내부 웹 접속을 확인했고, DB 정책은 별도로 다시 활성화했습니다.

처음에는 규칙 생성, 검사와 적용, 재부팅용 저장을 따로 실행했습니다. 이제 wg-update-policy.py를 한 번 실행하면 세 프로그램을 정해진 순서대로 호출합니다. 또 실제 변경 전에 실행 중인 방화벽 규칙과 재부팅용 설정 파일을 각각 백업하도록 했습니다. 복구 시험에서는 웹을 허용하는 규칙을 0개로 만든 뒤 실제 방화벽에 적용하고 파일에도 저장했습니다. 두 상태가 바뀐 직후 시험용 오류를 발생시켰습니다. 프로그램은 실행 중인 규칙과 저장 파일을 각각 백업 상태로 돌리고 내용이 일치하는지 확인했습니다. Windows에서도 웹페이지가 다시 열렸습니다. 시험 중에 꺼 둔 DB 정책은 시험을 마친 뒤 별도로 다시 활성화했습니다.

WireGuard 설정 비교와 변경 미리보기

DB와 WireGuard 사이의 차이를 적용 전에 확인할 수 있습니다.

마지막으로 DB에 기록한 VPN 주소가 WireGuard의 실제 설정과 일치하는지 확인하는 기능을 만들었습니다. 비교 대상은 DB의 현재 할당, 실행 중인 WireGuard 설정, 그리고 재부팅 때 사용하는 저장된 설정입니다. 처음에는 세 곳에서 같은 공개 키에 10.40.0.2가 연결돼 있었습니다. 시험에서는 DB 주소만 10.40.0.3으로 바꿨습니다. 검사기는 실행 중인 설정과 저장된 설정 모두에서 불일치를 찾았습니다. 미리보기에는 두 곳에서 기존 10.40.0.2/32를 10.40.0.3/32로 바꿀 필요가 있다고 표시됐습니다. DB를 10.40.0.2로 복원하자 두 곳 모두 변경할 항목이 없다고 나왔습니다.
